Я бы сейчас пошёл не в новый бизнес-модуль, а в **завершение execution pipeline**. У нас уже есть почти весь каркас, поэтому следующий логичный шаг — сделать его реально рабочим.

### Следующий этап

Я бы двигался так:

```text
1. Execution tests
        ↓
2. ExecutionReportHandler tests
        ↓
3. Position tests
        ↓
4. MarketEventHandler tests
        ↓
5. ScaledValue tests
        ↓
6. Application wiring
        ↓
7. Recording / Replay
        ↓
8. Exchange execution adapter
        ↓
9. Integration tests
```

### 1. Сейчас — `ExecutionReportHandler`

Это самый логичный следующий шаг.

Сейчас поток:

```text
Exchange
   │
   ▼
ExecutionReportHandler
   │
   ├──► Recorder
   │
   ├──► OrderManager::applyExecution()
   │
   └──► PositionManager::applyExecution()
```

Нужно написать:

```text
tests/execution/
├── order_manager_test.cpp
└── execution_report_handler_test.cpp   <-- NEW
```

Причём здесь очень хорошо использовать test doubles:

```cpp
TestRecorder
TestOrderManager
TestPositionManager
```

и проверять **именно orchestration**, а не бизнес-логику этих компонентов.

---

### 2. Затем `PositionManager` tests

Сейчас `Position` — довольно критичный компонент:

```text
ExecutionReport
       │
       ▼
PositionManager
       │
       ▼
Position
       │
       ▼
PnL
```

Нужно проверить:

```text
Buy  +10 → position +10
Buy  +5  → position +15
Sell -5  → position +10
Sell -10 → position 0
Sell -5  → position -5
```

И отдельно проверить average price / realized PnL, если это уже входит в текущую реализацию `Position`.

---

### 3. Затем `MarketEventHandler`

Сейчас у него фактически две ответственности orchestration:

```text
MarketEvent
    │
    ▼
MarketEventHandler
    ├──► Strategy
    └──► Recorder
```

Нужно убедиться, что обе downstream-системы получают **один и тот же event**.

---

### 4. `ScaledValue`

После того как мы вынесли:

```text
ScaledValue
    ↑
    ├── Price
    └── Quantity
```

обязательно нужны тесты.

Особенно:

```cpp
Price::fromInteger(100).raw() == 10'000'000'000
Quantity::fromInteger(5).raw() == 500'000'000
```

и arithmetic/comparison.

---

### 5. Потом `Application`

Вот здесь уже можно проверить весь dependency graph:

```text
Application
    │
    ├── MarketData
    ├── Strategy
    ├── Risk
    ├── Execution
    ├── Position
    ├── PnL
    └── Recording
```

Сейчас `Application` — фактически composition root, поэтому здесь важно убедиться, что зависимости направлены правильно.

---

### 6. После этого — Recording / Replay

Вот это я считаю **следующим большим функциональным модулем**.

Сейчас у нас:

```text
MarketEvent ──────► Recorder
ExecutionReport ──► Recorder
```

Но пока recorder — только endpoint.

Следующий шаг:

```text
                  ┌──────────────┐
MarketEvent ─────►│              │
                  │   Recorder   │────► Event Log
ExecutionReport ─►│              │
                  └──────────────┘
                                      │
                                      ▼
                                    Replay
                                      │
                                      ▼
                                   Strategy
```

И здесь уже можно будет сделать действительно интересную архитектуру:

```text
Live:

Exchange
   ↓
MarketData
   ↓
Strategy
   ↓
Execution


Replay:

Event Log
   ↓
Replay
   ↓
Strategy
   ↓
Execution simulation
```

То есть стратегия вообще не должна знать, работает она с live market data или replay.

---

## Поэтому мой следующий конкретный шаг

**`ExecutionReportHandler` + его тесты.**

После него:

**`PositionManager` tests → `MarketEventHandler` tests → `ScaledValue` tests → `Application` → `Recording/Replay`.**

Я бы пока **не добавлял новые trading-модули**. Архитектурный skeleton уже достаточно хороший; сейчас выгоднее довести существующий pipeline до состояния, когда каждый переход между модулями проверяется тестами.

через NIC проходит миллионы пакетов в секунду. Как связать входящий `T1` и исходящий `T2` для одного логического запроса-ответа?


## 🧩 Основные подходы к связыванию T1 и T2

### 1. **Сквозной контекст запроса в приложении** (самый распространенный)

Это классический подход в HFT-системах:

1. **При получении пакета (T1)**:
    - Приложение извлекает `T1` из заголовка пакета.
    - Парсит содержимое пакета (например, биржевой стакан или исполнение).
    - Генерирует уникальный идентификатор запроса (например, `request_id`), который будет использоваться для всех исходящих пакетов, связанных с этим входящим событием.

2. **При отправке ответа (T2)**:
    - Формируя исходящий пакет, приложение сохраняет в нем или в своей внутренней структуре тот же `request_id` (или явную ссылку на структуру входящего запроса).
    - Когда NIC проставляет `T2` и возвращает его в очередь событий, приложение получает этот штамп вместе с дескриптором отправленного пакета.

3. **Связывание**:
    - В структуре данных отправленного пакета приложение хранит ссылку на исходный запрос (например, указатель на `IncomingRequest`).
    - Когда приходит событие о завершении отправки с `T2`, оно содержит пользовательский контекст (например, `user_data` в дескрипторе), по которому можно восстановить исходный `T1`.

```cpp
// Пример (псевдокод) через ef_vi:
struct RequestContext {
    uint64_t t1;
    uint64_t request_id;
    // другие данные
};

// При получении пакета:
RequestContext* ctx = new RequestContext();
ctx->t1 = rx_packet->hw_timestamp;
ctx->request_id = generate_id();

// При отправке ответа:
TxDescriptor* desc = allocate_tx_descriptor();
desc->user_data = (uint64_t)ctx;  // сохраняем указатель на контекст
desc->payload = build_response(ctx->request_id);
send_packet(desc);

// Когда приходит событие с T2:
void on_tx_complete(TxEvent* event) {
    RequestContext* ctx = (RequestContext*)event->user_data;
    uint64_t t2 = event->hw_timestamp;
    uint64_t latency = t2 - ctx->t1 - optical_delay; // чистое время софта
    // ... используем ctx ...
    delete ctx;
}
```

### 2. **Использование порядковых номеров (sequence numbers)**

Некоторые биржи включают в протокол поле `sequence_number`, которое можно использовать для связывания:

- **Входящий пакет**: имеет `seq_num_in`.
- **Исходящий ответ**: приложение формирует ответ с тем же или производным `seq_num_out` (например, добавляет флаг `response`).
- **Таблица соответствий**: приложение ведет хэш-таблицу `seq_num -> T1`, куда сохраняет `T1` при получении. При отправке и получении `T2` делает lookup по `seq_num`.

Этот подход удобен, если протокол биржи (например, FIX/ITCH) поддерживает сквозные идентификаторы.

---

### 3. **Использование аппаратных очередей и привязка к потокам** (hardware flow steering)

Современные NIC (Solarflare/Xilinx) поддерживают **RSS** (Receive Side Scaling) и **flow steering**:

- Можно настроить карту так, чтобы пакеты с определенным `5-tuple` (IP, порт, протокол) всегда попадали в один и тот же RX-буфер и обрабатывались одним потоком CPU.
- Если все запросы/ответы для одной сессии проходят через один поток, то связывание `T1` и `T2` упрощается — достаточно хранить локальные структуры данных в потоке (per-thread maps).

Однако это не решает проблему глобально, а лишь уменьшает конкуренцию и упрощает синхронизацию.

---

### 4. **PTP-синхронизация и абсолютное время**

Если обе стороны (вы и биржа) используют PTP с общим мастером (например, GPS), то можно полагаться на абсолютное время:

- `T1` — время получения запроса на вашей стороне.
- `T2` — время отправки ответа с вашей стороны.
- Сама биржа также ставит свои временные метки в пакетах.

Тогда связывание становится логическим: ответ считается ответом на запрос, если он был отправлен после получения запроса и до таймаута. Но это менее точно, чем сквозной `request_id`, потому что возможны накладки при высокой частоте запросов.

## 🚀 Практическая реализация в HFT

В реальных системах обычно используется **гибридный подход**:

1. **В структуре исходящего пакета** есть поле `user_data` (или `cookie`), которое NIC возвращает вместе с `T2` в событии завершения отправки.
2. Это `cookie` используется как указатель на объект, содержащий `T1` и всю контекстную информацию.
3. Память под контекст выделяется из пула (memory pool) для минимизации аллокаций.
4. По завершению обработки контекст возвращается в пул.

```cpp
// Реальный паттерн через ef_vi (упрощенно):
ef_pd* pd = ...;
ef_vi* vi = ...;

// Отправка:
ef_request_id req_id;
ef_vi_transmit(vi, &tx_desc, 1, &req_id, cookie); // cookie = указатель на контекст

// Получение подтверждения с T2:
ef_event event;
while (ef_event_queue_poll(vi->evq, &event) > 0) {
    if (event.type == EF_EVENT_TYPE_TX_COMPLETE) {
        TxContext* ctx = (TxContext*)event.tx_complete.cookie;
        uint64_t t2 = event.tx_complete.timestamp; // аппаратный T2
        // ... вычисляем latency = t2 - ctx->t1 - optical ...
    }
}
```

## 📌 Итог

| Уровень | Ответственность |
|---------|-----------------|
| **NIC** | Ставит `T1` при приеме, `T2` при отправке, возвращает их приложению с дескриптором пакета |
| **Приложение** | Хранит пользовательский контекст (например, `request_id` → `T1`) и связывает его с исходящим пакетом через `cookie`/`user_data` |
| **Связывание** | Полностью на стороне приложения: структуры данных (хэш-таблицы, пулы контекстов) с ключом по `request_id` или указателю |

Таким образом, `T1` и `T2` не соответствуют "одной сессии" на уровне железа — это **логическое связывание**, которое реализует ваш код, используя аппаратные метки как сырые данные для измерения задержек.
